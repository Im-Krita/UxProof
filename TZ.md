# UXProof — техническое задание (MVP 0.1)

**Дата:** 15 ноября 2026. **Целевая среда:** Windows, desktop. **Формат:** приложение Tauri 2 с React UI, Rust backend и Playwright runner на Node.js. **Контекст:** заявка на ИТ-хакатон; демонстрация до 20 ноября 2026 (срок из предоставленного материала, не подтверждён в регламенте организаторов). **Статус:** частично реализованное ТЗ; степень проверки указана отдельно.

## 1. Концепция

UXProof — автоматизированный аудит **поведения интерфейса по сценарию**. Пользователь задаёт целевое веб-приложение, последовательность действий и ожидаемые результаты. Приложение открывает Chromium, повторяет сценарии в разных размерах экрана, собирает проверяемые факты и фиксирует рекомендации ИИ отдельно от технических дефектов.

Цепочка ценности: **сценарий → реальное действие → проверка результата → доказательство → исправление разработчиком → повторный прогон**.

Это не генератор оценок красоты интерфейса и не инструмент полноценных автоматических UX-исследований от лица человека.

### 1.1 Проблема

Разработчики часто тестируют страницу как отдельный экран, но теряют проблемы переходов и обратной связи: скрытая кнопка возврата на мобильном, отсутствие подтверждения сохранения, неочевидная потеря состояния, исключения JavaScript, нарушения доступности. Функциональный тест и визуальный AI-анализ существуют по отдельности и требуют ручного связывания.

### 1.2 Целевая аудитория

Инди-разработчик, небольшая веб-студия, QA-инженер, UI/UX-дизайнер и команда, проверяющая релиз или редизайн. За рамками MVP: мобильные нативные приложения, тестирование десктопных Win32-окон и production-grade cloud testing.

### 1.3 Проверяемая продуктовая гипотеза

Если у проверки есть **конкретный шаг и скриншот**, разработчику проще воспроизвести дефект, чем по общему AI-описанию «плохая UX-иерархия». Это гипотеза продукта; требуются пользовательские тесты, чтобы её подтвердить.

## 2. Объём релиза

### P0 — реализовать и показать

1. Создание проекта с именем и `http(s)` URL.
2. Преднастроенные 3 сценария и 3 размера экрана.
3. Редактирование названия и шагов сценария без написания тестового кода.
4. Не менее 10 поддерживаемых типов шагов Playwright.
5. Изолированный Chromium context для каждого сценария и разрешения.
6. Успех или провал каждого шага с технической причиной ошибки.
7. Снимок текущего состояния на каждый запуск сценария×разрешение.
8. Сканирование доступности по axe-core (выбранные WCAG-теги).
9. Сбор JavaScript page errors и фиксация horizontal overflow.
10. Представление проблем с `scenario`, `viewport`, `step`, `severity`, `description`, `screenshot`.
11. Сохранение JSON и HTML, история локальных отчётов.
12. Опциональная отправка изображений в модель, вывод в отдельной категории `recommendation`.
13. Запуск без ИИ-ключа (основная функциональность не зависит от LLM).
14. Тестовое веб-приложение с намеренными ошибками.
15. Tauri IPC: URL и действия валидируются Rust-слоем, UI не получает прямой доступ к `fs`/shell.

### P1 — после доказанного MVP

- Генерация последовательности действий из естественного языка с ручным подтверждением плана.
- Рекордер Playwright Codegen или запись кликов мышью с конвертацией в тест.
- Полноценный diff двух прогонов по стабильным идентификаторам дефектов, скриншотам и шагам; базовая сводка «до/после» уже присутствует в v0.1 для одинаковых сценариев/экранов.
- Поддержка auth state, test fixtures и автоматического сброса состояния между тестами.
- Скриншоты на **каждом шаге**, HAR/trace.zip, запись видео при падении.
- Использование MCP / Skills для подключения внешних браузеров, репозиториев, issue tracker.
- Автогенерация Playwright tests / GitHub Actions CI; read-only pull request comments.
- Проверка клавиатурной навигации, интерактивных размеров и состояния фокуса.
- Выделение повторяющихся находок на разных разрешениях (deduplication).

### P2 — продуктовая версия

- Инсталлятор Windows с **собственным bundled runtime и Chromium**; автообновления.
- Несколько браузеров и ОС; remote workers.
- Многостраничные обходы и безопасный AI-agent planner с политиками действий.
- Совместная работа, проекты/роли, CI-отчёты и SaaS-модель.
- Динамические API-моки и интеграции с Figma/GitHub.

**Отказ от преждевременных обещаний:** в v0.1 нет автономного agentic navigation по одному промпту, нет подтверждённой повышенной точности по сравнению с конкурентами, нет инсталлятора без внешних зависимостей.

## 3. Основные пользовательские потоки

### UX-01. Первая проверка

1. Открыть UXProof.
2. Увидеть демо-проект Relay и три сценария.
3. Убедиться, что demo/site работает по `http://127.0.0.1:4180`.
4. Нажать «Запустить аудит».
5. Получить результаты по всем выбранным разрешениям.
6. Найти ошибку на шаге и открыть её скриншот.
7. Скачать JSON/HTML и/или повторить после изменения приложения.

### UX-02. Собственный сайт

1. Ввести URL своего сайта.
2. Создать сценарий и последовательность шагов из 10 поддерживаемых операций.
3. Указать селекторы `role`, `label`, `css`, `testid`.
4. Выбрать размеры экрана.
5. Запустить проверку и просмотреть результаты.

### UX-03. Дополнительная рекомендация ИИ

1. Включить переключатель ИИ.
2. Выбрать `OpenAI` или `Ollama`.
3. Настроить credentials **в переменных окружения backend/runner**, не в браузере.
4. Запустить тест.
5. Получить рекомендации рядом с дефектами, но в **другой категории достоверности**.
6. При ошибке провайдера сохранить технические результаты и показать предупреждение.

## 5. Данные и схема

Конфигурация проекта:

```json
{
  "project":"Relay — демонстрационный аудит",
  "baseUrl":"http://127.0.0.1:4180",
  "scenarios":[{
    "id":"server",
    "title":"Выбор и подключение сервера",
    "description":"Проверка основного сценария",
    "steps":[{"type":"click","name":"Открыть список серверов","target":"role:button|Серверы","value":""}]
  }],
  "viewports":[{"id":"mobile","label":"Mobile","width":390,"height":844}],
  "options":{"enableAI":false,"aiProvider":"openai"}
}
```

Модель отчёта: `runId`, `project`, `baseUrl`, `startedAt`, `durationMs`, `options`, `summary`, `results[]`, `issues[]`, `warnings[]`.

- `results[]`: сценарий, экран, статус, список шагов, время, PNG.
- `issues[]`: `kind= functional|accessibility|javascript|overflow|ai-ux`, `status=confirmed|recommendation`, серьёзность, описание, сценарий, экран, PNG, дополнительное правило axe.
- `warnings[]`: недоступность LLM, сбой подсистемы axe, проблемы сохранения снимка.

`runId` генерируется Rust (`uuid`) в Tauri, либо Node (`crypto.randomUUID`) в режиме локального API. Файлы сохраняются по `runs/<runId>/`.

## 6. Архитектурные принципы

1. **Rust — доверенная граница десктопа.** Сопровождает процессы, проверяет входные данные, отвечает за каталог результатов и локальную файловую систему.
2. **Playwright Node runner — готовый механизм браузерных действий.** Переписывать Chromium automation на Rust ради формального «100% Rust» не требуется.
3. **React — интерфейс, не источник истины.** Не классифицирует дефекты по выдуманной оценке и не создаёт фиктивные тестовые результаты.
4. **LLM не решает, прошёл ли тест.** Только выдает отдельные UX-гипотезы по скриншоту. Отсутствие API не ломает технический аудит.
5. **Доказательство воспроизводимости важнее числа “AI insights”.** Каждая ошибка, где возможно, привязана к реальному шагу и снимку.
6. Запрещено без пометки изменять код проверяемого приложения; UXProof только взаимодействует с ним как пользовательский тест.

Подробная схема в `docs/ARCHITECTURE.md`.

## 7. Нефункциональные требования

- Язык UI: русский.
- Компоновка: утилитарный минимализм, компактные формы без гигантских декоративных блоков.
- Ошибка ≠ рекомендация: 2 разных класса с понятными значками и фильтрами.
- В desktop UI инструменты не получают произвольный FS/CLI доступ через JS.
- Один запуск выполняется последовательно: отдельной очереди фоновых заданий в v0.1 нет.
- Ограничение: 10 сценариев × 4 экрана × 30 шагов максимум; UI по умолчанию 3×3.
- Предел API-изображений: один кадр на проверку сценария, максимум 3 изображения на LLM за запуск.
- Изолированные контексты Playwright предотвращают наследование cookies между проверками (но не изменения серверного состояния).
- Хранение: локальные JSON, HTML, PNG без шифрования.
- Требования к надёжности: ошибка ИИ не прерывает автоматические проверки; ошибка запуска Chromium должна отображаться пользователю, а не выглядеть как пустой отчёт.

## 8. Безопасность

### Реализованные меры

- Исполнитель допускает только перечисленные 10 шагов, не поддерживает `eval`, произвольный JS или shell-скрипты из сценария.
- Rust запускает фиксированную команду `node`, не интерполирует введённый URL в shell.
- URL ограничен схемами HTTP/HTTPS; учетные данные в URL блокируются.
- Rust ограничивает путь к скриншоту `runId` и basename PNG; Node аналогично ограничивает свой HTTP API.
- HTML отчёт экранирует пользовательские строки от HTML-инъекции.
- Ключ OpenAI только в окружении Node/Rust.
- Локальный dev API привязан к `127.0.0.1` и требует специальный заголовок на запуск.
- Вызов Ollama ограничен loopback адресом.

### Не реализовано (блокеры production)

- Глобальная sandbox-изоляция тестируемого сайта.
- Запрет destructive actions по семантике кнопок.
- Полный сетевой allowlist: свой origin и loopback (если проект сам локальный) разрешены, служебные и чужие частные адреса блокируются. Произвольный обход всей LAN по-прежнему не является режимом «песочницы браузера».
- Полноценный CSP и packaged runtime hardening.
- Система хранения учётных данных/логинов.
- Защита от DoS при огромных ответах браузера, экранов или ошибочных циклах.

Для реального проекта используйте тестовое окружение и данные. Нельзя запускать сценарии против чужих сайтов без разрешения.

## 9. Демонстрация для конкурса

**Проверяемая постановка:** на тестовом приложении Relay в разделе настроек после нажатия «Сохранить» отсутствует явный `role=status`. На маленькой ширине скрыта кнопка «На главную». Приложение UXProof должно показать, какие сценарии и на каких экранах не проходят.

**План защиты, 2–3 минуты:**

1. Показать Relay и сценарии.
2. Запустить браузерный аудит.
3. Открыть технический дефект «Увидеть подтверждение сохранения», скриншот и шаг.
4. Показать, что «Возврат на главную» воспроизводится на desktop, но падает на mobile.
5. Исправить `demo/index.html` вручную, перезапустить аудит и сравнить результаты.
6. Показать разделение дефектов и рекомендаций ИИ; если нет рабочего API, не подменять его демонстрационными данными.

**Условия сравнения:** исходный код тестового приложения должен быть одинаковым между проверяемыми окружениями; повторный прогон фиксирует новую версию. Не выдавать скрипт с заведомо запрограммированным результатом за AI-автономность.

## 10. Метрики эксперимента (не результаты)

| Метрика | Как измерять | Порог демонстрационного эксперимента (целевой, не факт) |
|---|---|---|
| Recall на размеченных дефектах | Найденные подтверждённые / все размеченные | 2/2 намеренных ошибки Relay |
| False positives | Ошибочные alerts / все alerts | Отслеживать отдельно по типам |
| Reproducibility | Сколько дефектов повторяется в N прогонах | 3 подряд для двух контрольных проблем |
| Стабильность запуска | Успешные запуски / все попытки | 100% на настроенной тестовой машине |
| Разделение доверия | Доля рекомендаций с маркировкой recommendation | 100% |
| Скорость | Время аудита 9 комбинаций | Измерить на конкретном ПК |

Запрещено выдавать эти желаемые значения за измеренные показатели.

## 11. Ограничения решения

- Desktop release installer не собран и не протестирован.
- Runner зависит от Node.js и установленного Chromium.
- Внешние UI на основе Canvas, WebGL, нативных диалогов и Shadow DOM могут потребовать иной стратегии локаторов.
- Наличие `Playwright success` гарантирует только выполнение **указанных** проверок, не отсутствие UX-дефектов.
- Axe-core видит не все нарушения WCAG, нужен ручной аудит.
- ИИ работает по ограниченному набору изображений, не наблюдает все micro-interactions.
- Состояние внешнего бэкенда может меняться между сценариями: изоляция браузерных контекстов не сбрасывает серверную БД.
- Текущая версия не содержит встроенного браузерного планирования действий по описанию «подключись к серверу» без сценария.

## 12. Приёмка

Если на стенде используется облачная модель — выполнить минимум 1 настоящий API-вызов без демонстрационных заглушек.
